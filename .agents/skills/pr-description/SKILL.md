# PR Description

本文だけで「なぜ必要か」「何が変わるか」「どこを確認すべきか」が分かる状態にする。作成前に親 Issue、diff、検証結果、外部操作の実施状況を照合し、未確認の事実を補わない。

次をこの順で記載する。

1. 背景と対応方針
2. コード・設定の変更と振る舞いへの影響
3. 動作確認（シナリオ、前提、結果）
4. 人間レビューで確認したいこと（なければ `なし`）
5. 残存リスクまたは意図的な未実施事項

親 Issue の全受け入れ条件を満たす PR は `Closes #<issue>` を含める。部分対応は `Refs #<issue>` と残作業を記載する。skill の利用だけを PR 更新権限として扱わず、外部操作は依頼範囲に従う。
